WebRTC & IP leaks

Proxy Switchboard · Keeping your real IP hidden when a proxy is on

Even with a proxy turned on, a feature called WebRTC can reveal your real IP address. This guide explains why, and how to stop it on both desktop and mobile.

Why WebRTC can leak

WebRTC (used by video calls, voice chat, and some websites for peer-to-peer connections) discovers your public IP by talking to STUN servers over UDP, directly. That direct UDP path goes around an app-level SOCKS/HTTP proxy — which only carries the TCP connections the browser explicitly sends to it. So ordinary requests correctly show the proxy's IP, while WebRTC can still expose your real one — including your real IPv6 address, even when the rest of your IPv6 is disabled.

Test it yourself: with the proxy on, open browserleaks.com/webrtc (or /ip). Under WebRTC, the Public IP should be your proxy's IP (or blank) — not your real one. Check both IPv4 and IPv6.

Mobile — Android & iOS

On mobile, Proxy Switchboard runs as a system VPN (Android VpnService / iOS Network Extension). That is full tunnel-mode: it captures every connection your device makes, including the UDP that WebRTC uses. So when the proxy is on, WebRTC is routed through your proxy or blocked — it cannot reach out directly to leak your real IP.

  • No extra setup. Simply make sure the proxy is connected (the VPN key icon is showing) before you open the browser or app.
  • See the caveat on UDP-capable proxies below — it decides whether WebRTC works via the proxy or is simply blocked (both are safe; neither leaks).

Desktop — macOS, Linux & Windows

On desktop the proxy is a local SOCKS/HTTP listener by default, which cannot see WebRTC's direct UDP. You have two ways to close the leak.

Option A — TUN mode (recommended)

TUN mode routes all of your device's traffic through a virtual network interface — including UDP — so WebRTC is covered automatically, for every app, with no per-browser configuration.

  • Enable it in Settings → Advanced → TUN mode (or the menu-bar toggle), then turn the proxy on.
  • It needs administrator rights (TUN runs as root), so turning the proxy on will prompt for your password.
  • WebRTC's UDP is then sent through your proxy (if it's a UDP-capable SOCKS5) or dropped (if not) — see the caveat below.
  • Leave “UDP direct fallback” off (the default). Turning it on lets UDP escape directly when the route can't carry it, which can leak.

Option B — Browser setting (if you prefer SOCKS mode)

If you keep using the plain SOCKS/HTTP proxy, force your browser to stop sending WebRTC UDP directly:

  • Chrome / Edge / Brave: install a WebRTC-control extension (e.g. “WebRTC Network Limiter” / “WebRTC Leak Prevent”) and set it to “Use my proxy server (if present)” — this sets the policy WebRTCIPHandlingPolicy = disable_non_proxied_udp, so WebRTC only goes through the proxy. (Managed devices can set that policy directly.)
  • Firefox: open about:config and set media.peerconnection.ice.proxy_only = true (route ICE only via the proxy), or media.peerconnection.enabled = false to disable WebRTC entirely.
  • Safari: Safari doesn't expose a reliable WebRTC-only-via-proxy switch — use TUN mode (Option A) instead.

Caveat: does your proxy carry UDP?

WebRTC is UDP. Whether it works through the proxy or is simply blocked depends on the proxy type your traffic is routed to — but in all safe cases your real IP stays hidden:

RouteWebRTC result
SOCKS5 with UDP supportWorks — exits via the proxy IP.
SOCKS5 without UDP, or SSH / HTTP / BlockBlocked — WebRTC gets no address (no leak).
Direct (no proxy for that host)Uses your real IP — by design, that route is unproxied.

So for WebRTC to actually function through the proxy (rather than just be blocked), your default proxy — or the rule the STUN host matches — should be a SOCKS5 server that supports UDP ASSOCIATE. SSH and HTTP proxies can't carry UDP; WebRTC is safely dropped instead.

Verify

  1. Turn the proxy on (TUN mode on desktop; VPN connected on mobile).
  2. Open browserleaks.com/webrtc.
  3. The WebRTC Public IP should show your proxy location — or be empty — and must not match your real IPv4 or IPv6.
